The research question
The setup

BioGuider is an automated documentation fixer for biomedical software repositories. It reads a package's README, installation guide, and tutorials, spots flaws (typos, broken links, wrong gene symbols, unclear instructions), and rewrites the sections that need help — so that a biologist who just cloned Seurat or scanpy can actually run the example.

The hard question isn't "does it produce output?" — every language model produces output. The hard question is: does the fix land on the right errors, and does it stop there? A model that rewrites your entire README from scratch loses your voice and your lab's conventions. A model that misses three-quarters of the bugs is useless.

Measuring this on real-world docs is impossible — you don't have a ground-truth "correct" version to compare against. So we borrow a trick from wet-lab QC: spike in a known amount of contamination, then measure recovery.

1
The experiment — spike-in recovery
STEP 01
Start with a clean sample
Ground truth
Take a real, known-good tutorial — the Seurat differential expression vignette. Thousands of researchers have read it; the maintainers have vetted it. Treat this as the pristine reference.
Analogy: your reference genome, pre-alignment.
STEP 02
Inject known errors
Controlled corruption
Use a separate "attacker" model to introduce N specific, labeled errors into the tutorial — typos, flipped cell-type markers, wrong hyperparameters, swapped accession IDs. Every error is logged with its exact original and mutated text.
Analogy: spiked-in ERCC controls at a known concentration.
STEP 03
Run models on corrupted version
The thing we're measuring
Hand the corrupted document to each candidate language model and ask it to fix all errors. The model doesn't see the clean version — only the corrupted one, and its own prior knowledge of biology and good writing.
Analogy: your pipeline processes the sample blind to the spike-in identity.
STEP 04
Score recovery
Quantify
For each logged error, check whether the model's output restored the original correct text. Compute precision (did it avoid breaking things that weren't broken?) and recall (did it catch the planted errors?) and combine into an F1 score.
Analogy: your final ERCC recovery curve — %detected vs. %ground-truth.
2
What we actually benchmark against — three axes
Axis A
Dose-response — does it hold up at scale?
Run the same experiment at increasing error density: 10 → 30 → 50 → 100 → 200 → 300 errors injected into the same document. A good model fixes a 10-error version near-perfectly; we want to know the breakpoint — the error count at which performance collapses. Models that fail gracefully at 300 errors are qualitatively different from ones that cliff-edge at 50.
↳ Figure 1: F1 vs. error count, one line per model.
Axis B
Model comparison — which tool for the job?
Same corrupted document, five different models. Compare: a closed-source flagship (GPT-5.4), two mid-tier open-weight models (Kimi-K2.5, GLM-5), a small open-source baseline (GPT-OSS), and a legacy baseline (GPT-4o). We learn which family of models actually reads biomedical text carefully — and whether the premium tier is worth the premium price.
↳ Figure 2: mean F1 per model with 95% CI across all error doses.
Axis C
Domain specificity — does it know biology?
Errors are stratified into generic text, bio-generic, and biomed-app-specific categories (see Section 3). A model can ace typos and still fumble a swapped cell-type marker. The heatmap tells us where each model breaks down — which is the actionable insight for choosing a model for a given lab's docs.

The error taxonomy — what we inject, and why
Difficulty
What it tests
Example injections
Why it matters
LEVEL 1
Generic text
Whether the model can proofread at all. Basic literacy, not biology.
Categories
typo · broken link · duplicated sentence · broken markdown list · missing code-fence language tag
Floor test. Any model worth considering should score near-perfectly here. Failures indicate the model isn't even reading carefully.
LEVEL 2
Bio-generic
Whether the model knows general bioinformatics vocabulary — the kind a competent graduate student picks up in year one.
Categories
gene-symbol case (tp53 → TP53) · species swap (mm10 ↔ GRCh38) · UMI vs. read count · batch correction vs. normalization terminology · 0- vs. 1-based coordinates · FASTQ/BAM/MTX file-format mix-ups
Tests whether the model has basic bio-literacy. Most modern LLMs do well; differences start to emerge on subtle cases like UMI/read confusion.
LEVEL 3 NEW
Biomed-app-specific
Whether the model understands the specific analytical context of modern biomedical tools — scRNA-seq clustering, differential expression, annotation workflows. This is the hard tier.
Categories (added in this refactor)
reproducibility drift — set.seed(42) changed, Seurat v4 ↔ v5
analysis hyperparameter — Leiden resolution 0.5 → 2.0, UMAP n_neighbors drift
statistical test mis-naming — "Wilcoxon" called "t-test", FDR ↔ Bonferroni
annotation ID-space confusion — GEO accession GSE → GSM, Ensembl ID corrupted
cell-type marker errors — CD4 ↔ CD8 swap, FOXP3 → RORC
This is what separates a model that can generically fix English prose from one that can actually steward a biomedical tutorial. A wrong marker gene in a tutorial sends every downstream user off the rails. This tier is what a biologist should care about most.

A worked example — what one test cell looks like
Corrupted input (5 injected errors shown)
# Differential Expression in Seurat v5 set.seed(43) markers <- FindMarkers( pbmc, ident.1 = "CD8_T_cell", ident.2 = "B_cell", test.use = "t.test", resolution = 2.0 ) # data from GSM123456
Target (original, what the fixer should recover)
# Differential Expression in Seurat v4 set.seed(42) markers <- FindMarkers( pbmc, ident.1 = "CD4_T_cell", ident.2 = "B_cell", test.use = "wilcox", resolution = 0.5 ) # data from GSE123456
Five errors, one per biomed-app category: reproducibility_drift (Seurat v4→v5), reproducibility_drift (seed 42→43), celltype_marker (CD4→CD8), stat_test_misnaming (wilcox→t.test), analysis_hyperparam (resolution 0.5→2.0), annotation_id_space (GSE→GSM). A fix-rate of 5/5 = perfect recall on this cell. A model that silently leaves "Seurat v5" alone (plausibly thinking it's an upgrade) would score 4/5 and get penalized — that's the point.

Why this matters for biomedical researchers
The use case

The documentation of a biomedical package is the primary UX for every first-time user — and in many labs, first-time users are rotating graduate students who will decide whether to adopt or abandon a tool within 30 minutes. A tutorial with a swapped marker gene, a drifted seed, or a broken install command costs real research hours and, occasionally, publishable conclusions. Package maintainers know this; most don't have time to systematically audit their own docs.

BioGuider aims to be an automated auditor — but you can't deploy an auditor you can't trust. A benchmark like this one is how we decide, empirically, whether a given language model is careful enough to let loose on community documentation. The output isn't a single number; it's a structured profile of where each model fails, so we can either pick a model that covers the cases we care about, or refuse to automate the cases where no current model is good enough.

The biomed-app-specific tier (Level 3) is the one that matters most for this goal. Generic typo fixing is commodity; knowing that CD4 is the helper-T marker and swapping it for CD8 is a scientific error, not a stylistic choice is not. That's the line we are measuring.

Target document: Seurat DE vignette (de_vignette.Rmd) — single-file stress bench, one highly-cited tutorial from a widely-used scRNA-seq package.
